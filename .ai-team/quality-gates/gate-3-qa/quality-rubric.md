# QA 品質評分標準

> 版本: v1.0
> 更新日期: 2026-03-19

---

## 評分維度與權重

| 維度 | 權重 | 滿分 | 評估重點 |
|------|------|------|----------|
| **功能完整性** | 25% | 25分 | 需求覆蓋、邊界處理、錯誤處理 |
| **程式碼品質** | 25% | 25分 | 可讀性、命名、複雜度、設計模式 |
| **測試覆蓋率** | 20% | 20分 | 單元測試、整合測試、邊界測試 |
| **文件完整性** | 15% | 15分 | 程式碼註解、API 文件、變更記錄 |
| **安全性** | 15% | 15分 | 輸入驗證、權限檢查、漏洞掃描 |

---

## 詳細評分標準

### 1. 功能完整性 (25分)

| 分數 | 標準 |
|------|------|
| 21-25 | 完全實現所有需求，邊界條件處理完善，錯誤處理周全 |
| 16-20 | 主要功能完成，少數邊界條件未處理 |
| 11-15 | 核心功能完成，部分需求未實現 |
| 6-10 | 功能不完整，有明顯缺失 |
| 0-5 | 功能嚴重缺失，無法正常使用 |

**檢查項目:**
- [ ] 所有需求都已實現
- [ ] 邊界條件處理完善
- [ ] 錯誤處理機制完整
- [ ] 異常情況有適當回應

---

### 2. 程式碼品質 (25分)

| 分數 | 標準 |
|------|------|
| 21-25 | 程式碼清晰易讀，命名精確，設計模式運用得當 |
| 16-20 | 整體良好，少數命名或結構可優化 |
| 11-15 | 可讀性一般，有明顯改進空間 |
| 6-10 | 程式碼混亂，難以理解 |
| 0-5 | 程式碼品質差，需要重寫 |

**檢查項目:**
- [ ] 命名清晰且一致
- [ ] 函數/類別職責單一
- [ ] 避免重複程式碼 (DRY)
- [ ] 適當使用設計模式
- [ ] 複雜度在合理範圍

---

### 3. 測試覆蓋率 (20分)

| 分數 | 標準 |
|------|------|
| 17-20 | 覆蓋率 > 90%，包含邊界和異常測試 |
| 13-16 | 覆蓋率 80-90%，主要路徑都有測試 |
| 9-12 | 覆蓋率 70-80%，基本功能有測試 |
| 5-8 | 覆蓋率 50-70%，測試不足 |
| 0-4 | 覆蓋率 < 50%，幾乎無測試 |

**檢查項目:**
- [ ] 單元測試覆蓋主要邏輯
- [ ] 整合測試驗證整體流程
- [ ] 邊界條件測試
- [ ] 錯誤情況測試

---

### 4. 文件完整性 (15分)

| 分數 | 標準 |
|------|------|
| 13-15 | 文件完整，包含使用說明、API 文件、變更記錄 |
| 10-12 | 主要文件齊全，部分細節可補充 |
| 7-9 | 基本文件存在，但不完整 |
| 4-6 | 文件嚴重缺失 |
| 0-3 | 幾乎無文件 |

**檢查項目:**
- [ ] README 說明清晰
- [ ] 程式碼註解適當
- [ ] API 文件完整
- [ ] 變更記錄 (CHANGELOG) 已更新

---

### 5. 安全性 (15分)

| 分數 | 標準 |
|------|------|
| 13-15 | 安全性考量周全，無已知漏洞 |
| 10-12 | 基本安全機制完善 |
| 7-9 | 有基本安全意識，部分可加強 |
| 4-6 | 有明顯安全隱患 |
| 0-3 | 嚴重安全問題 |

**檢查項目:**
- [ ] 輸入資料驗證
- [ ] 權限檢查機制
- [ ] 敏感資訊保護
- [ ] 無已知安全漏洞

---

## 評分等級與處理方式

| 總分 | 等級 | 處理方式 |
|------|------|----------|
| 90-100 | A (優秀) | ✅ 直接通過 |
| 80-89 | B (良好) | ✅ 小修正後通過 |
| 70-79 | C (可接受) | ⚠️ 需修改後重新評分 |
| 60-69 | D (需改進) | ❌ 退回開發階段 |
| <60 | F (不合格) | ❌ 重新設計實作 |

## 特殊情況處理

### 緊急修復
- 可適度降低標準
- 但必須通過自動化檢查
- 事後補全測試和文件

### 實驗性功能
- 文件要求可放寬
- 但程式碼品質仍需達標
- 明確標記為實驗性

### 核心功能
- 嚴格執行所有標準
- 必須達到 A 或 B 等級
- 需要詳細的文件和測試
